# 10 - 一条 CAN 总线控制 7 个无刷电机够不够

结论：**电气和协议上完全够，7 个节点对 CAN 来说很少；关键是更新率和总线负载。**

CAN 2.0 标准帧最多 8 字节数据，CANopen 节点 ID 最多 127 个，7 个电机只占很小一部分。

## 1. 先算带宽

经典 CAN 标准数据帧（11 位 ID + 8 字节数据）大约 108–130 位（含位填充），按 125 位估算：

| 波特率 | 一帧时间（约） | 理论帧率上限 |
|---|---:|---:|
| 500 kbit/s | 250 µs | 约 4000 帧/s |
| 1 Mbit/s | 125 µs | 约 8000 帧/s |

假设每个电机每个控制周期：

- 1 帧命令（8 字节）
- 1 帧反馈（8 字节）

7 个电机 = 每周期 14 帧。

| 控制频率 | 帧率 | 500k 负载 | 1M 负载 |
|---|---:|---:|---:|
| 100 Hz | 1400 帧/s | 约 35% | 约 17% |
| 200 Hz | 2800 帧/s | 约 70% | 约 35% |
| 500 Hz | 7000 帧/s | **超 100%，不够** | 约 87% |
| 1000 Hz | 14000 帧/s | **严重超载** | **约 175%，不够** |

这是“命令 + 反馈都每个周期发”的保守估算。实际还要加上：

- 心跳、状态、错误帧；
- CANopen SDO/PDO 映射；
- 其他传感器/IO 节点；
- 重传和错误帧。

## 2. 推荐配置

| 场景 | 建议 |
|---|---|
| 100–200 Hz 控制 | **500 kbit/s 够用**，留 30% 以上余量 |
| 500 Hz–1 kHz 控制，7 个电机，命令+反馈 | **1 Mbit/s**，并压缩 PDO 数量/数据长度 |
| 1 kHz 以上，或每个电机要传电流、温度、编码器、错误码 | 考虑 **CAN FD** 或 **两条 CAN 总线** |
| 只发命令、反馈降频 | 500k/1M 都能更宽裕 |

实际项目中建议：

1. 先定控制周期（比如 1 kHz）和每周期必须交换的数据量；
2. 用 `canbusload`（Linux）或分析仪统计真实负载；
3. 目标总线负载 **不超过 50–60%**，给重传和突发留余量。

## 3. 电气和布线

- **终端电阻**：总线物理两端各 120Ω，中间节点不要都接；7 个电机不要每个都开终端。
- **拓扑**：主干 + 短支线，支线尽量 < 0.3 m；不要星型长支线。
- **线材**：双绞线，最好屏蔽；CAN_H/CAN_L 成对。
- **共地**：非隔离节点必须共地；电机驱动器干扰大时用隔离 CAN 收发器。
- **隔离**：T-2Can 两路都是隔离的；CANable 不隔离，台面测试没问题，上电机后注意地环路和干扰。
- **总线长度**：500k 建议 < 100 m，1M 建议 < 40 m；实际看线材和节点数。

## 4. 协议层

- 每个电机分配唯一节点 ID（CANopen 1–127）；
- 用 PDO 传周期数据，SDO 只做参数配置；
- 主站按固定周期发命令，反馈可以每周期一帧或降频；
- 急停/使能建议用高优先级 ID 或独立硬线，不要只依赖 CAN；
- 上电先做节点扫描/心跳，确认 7 个节点都在线。

## 5. 用 CANable / T-2Can 做控制主站可以吗

不建议做**闭环控制主站**：

- USB-CAN 的延迟和抖动在毫秒级，不适合 1 kHz 硬实时；
- slcan 是文本协议，吞吐和实时性都受限；
- 它们更适合抓包、调试、下发测试命令。

正式控制建议用 MCU（STM32、ESP32、Jetson + CAN 控制器）做主站，
CANable/T-2Can 挂在总线上做分析仪/第二节点。

## 6. 结论

- **一条 CAN 总线带 7 个无刷电机：够。**
- 100–200 Hz：500k 经典 CAN 足够；
- 500 Hz–1 kHz：建议 1M，且控制 PDO 数量；
- 更高频率或大数据量：CAN FD 或双总线；
- 真正决定成败的是**总线负载、终端、布线和主站实时性**，不是“7 个节点”这个数量。
